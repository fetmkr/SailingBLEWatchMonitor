# SailingBLEWatchMonitor

요트 텔레메트리 모노레포.

보드가 속도·침로·기울기를 BLE 로 뿌리고, 아이폰과 애플워치 앱이 받아 실시간으로
보여준다. 배 이름은 **`random()`** 이고 광고에는 `SAIL-random()` 으로 나간다.

**펌웨어가 두 벌이다. 지금 쓰는 것은 RAK 쪽이다.**

| | 보드 | 상태 |
|---|---|---|
| [`firmware-rak/`](firmware-rak/README.md) | RAK3312(ESP32-S3) + RAK19007 | **지금 쓰는 것.** GPS·9축·화면·SD |
| [`firmware/`](firmware/README.md) | Adafruit ESP32-S3 TFT Feather | 예전 것. 가상 데이터만. 손대지 않음 |

칩은 둘 다 ESP32-S3 지만 보드·핀·붙는 모듈이 전부 달라서 폴더를 나눴다.
기존 쪽은 실기기 검증이 끝난 상태라 건드리지 않는다.

```
.
├── PROTOCOL.md      ← 패킷 규격 (단일 진실 공급원)
├── firmware-rak/    ← RAK3112 펌웨어. GPS(L76K) · IMU(MPU-9250) · OLED · SD
├── firmware/        ← Feather TFT 펌웨어 (가상 데이터, 내장 240x135 화면)
├── app/             ← Xcode 프로젝트 (SwiftUI, iOS + 독립 실행 watchOS)
└── tools/
    ├── verify.sh              ← 하드웨어 없이 돌리는 전체 검증
    └── swift_decode_check/    ← C++ 인코더 ↔ Swift 디코더 교차 검증기
```

## 빠른 시작

```bash
# 1) 펌웨어 굽기 (지금 쓰는 보드)
cd firmware-rak
pio run -t upload --upload-port "$(ls /dev/cu.usbmodem* | head -1)"
pio device monitor          # 시리얼에서 check 를 치면 붙어 있는 것을 한 번에 훑는다

# 2) 앱
cd ../app && xcodegen generate && open SailingMonitor.xcodeproj
#    아이폰: 스킴 SailingMonitor  + 기기 hojun            → ⌘R
#    워치  : 스킴 SailingMonitor Watch App + 기기 워치     → ⌘R
```

> 포트 이름은 다시 꽂을 때마다 바뀐다 (`usbmodem1101` ↔ `usbmodem101`).
> 고정해 두지 말고 위처럼 찾아 쓸 것.

자세한 건 [`firmware-rak/README.md`](firmware-rak/README.md) 와
[`app/README.md`](app/README.md).

## 프로토콜 요약

전체 규격은 [`PROTOCOL.md`](PROTOCOL.md).

| | |
|---|---|
| 디바이스 이름 | `SAIL-<이름>` — 보드마다 고유. 예) `SAIL-hojun` |
| Service UUID | `B0A70001-0000-4000-8000-000000000001` |
| Telemetry Characteristic | `B0A70002-0000-4000-8000-000000000001` (Read + Notify) |
| Notify | **12바이트**(Feather) 또는 **37바이트**(RAK, 9축·GPS 상태 포함) / 기본 10 Hz |
| Advertising | legacy, 200 ms. Manufacturer Data(9바이트 + seq) 를 1 Hz 로 갱신 |

**규격은 네 곳에 구현되어 있고 항상 함께 고쳐야 한다.**

| 역할 | 파일 |
|---|---|
| 문서 | `PROTOCOL.md` |
| 펌웨어 인코더 (RAK) | `firmware-rak/include/protocol.h` |
| 펌웨어 인코더 (Feather) | `firmware/include/protocol.h` |
| 앱 디코더 | `app/Shared/Protocol.swift` |

두 펌웨어가 **서로 다른 길이를 보내는 것이 정상이다.** RAK 은 12바이트 뒤에
9축과 GPS 상태를 덧붙여 37바이트로, Feather 는 9축이 없어 12바이트로 보낸다.
`PROTOCOL.md` §7 이 "길면 앞부분만 파싱" 을 규정하므로 앱은 양쪽을 다 받는다.

세 개가 어긋나는 걸 막으려고 교차 검증기를 붙여 뒀다 (아래).

## 하드웨어 없이 검증하기

```bash
./tools/verify.sh          # 전부 (펌웨어 컴파일 + 앱 빌드 포함, 수 분)
./tools/verify.sh quick    # 로직/프로토콜만 (수 초)
```

| 단계 | 내용 |
|---|---|
| 1 | 펌웨어 로직 호스트 검증 — 인코딩 바이트, 시뮬레이션 궤적, 값 범위, 배터리 감소 |
| 2 | **C++ 인코더 → Swift 디코더 교차 검증** (192개 골든 벡터) + TFT 레이아웃 넘침 검사 |
| 3 | 펌웨어 실제 컴파일 (RAK3112 + Feather TFT + DevKit) |
| 4 | iOS / watchOS 앱 빌드 |

2단계가 이 저장소의 핵심 안전장치다. 펌웨어가 실제로 뱉는 바이트열을
앱 디코더에 그대로 먹여 값이 일치하는지 본다. 엔디안·오프셋·부호 실수는 여기서 잡힌다.

시뮬레이터에서는 CoreBluetooth 가 동작하지 않으므로(상태 `unsupported`)
**BLE 동작 자체는 반드시 실기기에서 확인**해야 한다.

## 수락 기준 체크리스트

실기기에서 확인할 항목.

| # | 항목 | 어디서 확인 |
|---|---|---|
| 1 | 아이폰에서 설정한 주기대로 속도가 부드럽게 갱신 | 설정 탭 **수신율**이 보드 설정값(기본 10 Hz) 근처 |
| 2 | 스캐너 탭에서 연결 없이도 속도 변화가 1 Hz 로 보임 | 스캐너 탭의 **갱신** 값이 1.00 Hz 근처, seq 가 1씩 증가 |
| 3 | ESP32 리셋 시 양쪽 앱 모두 3초 내 자동 재연결 | 보드 `RST` 버튼 → 디버그 로그의 `재연결 완료 — N초 걸림` |
| 4 | 워치: 손목 내렸다 들면 값이 곧바로 복구 | 상단 점이 초록이고 값이 회색이 아니면 성공 |
| 5 | 워치 앱 스와이프 종료 후 재실행 시 1~2초 내 재연결 | 상태 배지가 곧바로 "연결됨" |
| 6 | 모듈이 여러 대여도 내가 고른 것에만 붙음 | 설정에서 고른 이름이 계속 유지, 로그에 `다른 모듈에 붙음` 이 없음 |
| 7 | 워치 액션 버튼으로 앱 실행 | 설정 → 액션 버튼 → 운동 → 앱 목록에 Sailing Monitor |

4번 참고: 지금은 **워크아웃 세션을 쓴다** (`HKWorkoutSession(.sailing)`, 앱을 켜면
자동 시작). 그래서 손목을 내려도 앱이 화면에 남고 BLE 도 유지된다. Always On
상태에서는 갱신이 초당 1회로 떨어지므로, 그때는 COG·힐을 숨기고 속도만 84pt 로
키운다. 초당 1회로도 읽을 값만 남기는 것이다.

> 세션이 안 돌면 손목을 내리는 순간 시계 화면으로 넘어가고 연결이 끊긴다.
> 워치 3페이지(설정)에서 **`항해 중 mm:ss`** 인지, **`어두워짐`** 횟수가 올라가는지로
> 확인한다.

## 모듈 선택 (여러 대 운용)

보드마다 이름이 다르고, 앱은 사용자가 고른 모듈에만 붙는다.

```bash
# 보드에 이름 붙이기 (USB 연결 후 시리얼 모니터에서)
name random()       →  SAIL-random(), module_id 160
```

이름에는 영숫자와 `-`, `_`, 그리고 괄호를 쓸 수 있다 (이 배 이름이 `random()` 이다).

이름을 설정하지 않으면 MAC **뒤쪽** 2바이트로 자동 생성되므로
(`3C:DC:75:70:2F:B5` → `SAIL-2FB5`), 아무 설정 없이 여러 장을 구워도 서로 구분된다.
앞쪽 바이트는 Espressif OUI 라 모든 보드가 같으니 쓰면 안 된다.

앱에서는 **설정** 화면에서 주변 모듈 목록(가까운 순)을 보고 하나를 고른다.
한 번 고르면 저장되어 다음부터는 자동 연결되고, "다른 모듈 선택"으로 해제할 수 있다.

옆 배 모듈에 붙지 않도록 3단으로 막는다 — 자세한 규약은 [`PROTOCOL.md §6`](PROTOCOL.md).

1. 스캔 자체를 Service UUID 로 필터 (오디오 기기 등은 콜백조차 안 옴)
2. 연결 전에 광고 이름이 고정한 이름과 같은지 확인
3. 연결 후 **매 패킷**의 `module_id` 검증 — 다르면 즉시 끊고 재탐색

3번이 핵심이다. 앱은 빠른 재연결을 위해 주변장치 식별자를 저장해 두고 스캔 없이
바로 연결하는데, 그 지름길은 2번을 건너뛰기 때문이다.

> 주변장치 식별자는 중앙장치마다 다른 값이라 아이폰의 선택을 워치가 물려받을 수 없다.
> 각 기기에서 한 번씩 골라야 한다.

## 여러 기기가 동시에 볼 때

모듈은 **연결을 1대만 받는다.** 한 대가 붙으면 광고를 non-connectable 로 바꾼다.
그런데 광고 자체는 계속 나가고, 앱에는 광고 폴백이 있다. 그래서 이렇게 된다.

```
워치가 먼저 연결   → 슬롯 차지          → 10 Hz (GATT notify)
아이폰은 연결 실패 → pending connect 유지 + 스캔 계속
                  → 광고에서 값을 뽑음  →  1 Hz
```

슬롯을 못 잡은 쪽도 **화면이 죽지 않고 1 Hz 로 내려앉는다.** 먼저 붙은 쪽이
연결을 놓으면 기다리던 쪽이 자동으로 올라간다(pending connect 라 즉시).

관전자·코치보트처럼 여럿이 봐야 하면 광고만으로 충분하다. 인원 제한이 없다.

> 슬롯을 늘려도(NimBLE 기본 3) 데이터가 감춰지지는 않는다. 속도·침로는 이미
> 광고로 평문 브로드캐스트 중이다. 정말 막으려면 화이트리스트나 페어링+암호화가 필요하고,
> 그러면 광고에 텔레메트리를 실을 수 없게 되어 설계가 크게 바뀐다.

## 알아두면 좋은 설계 포인트

- **연결 중에도 광고가 계속된다.** 연결되면 `ADV_IND` → `ADV_SCAN_IND` 로 바꿔
  non-connectable 이지만 scannable 인 상태를 유지한다. 그래서 아이폰이 연결해 있는
  동안에도 다른 기기(또는 같은 앱의 스캐너 탭)에서 브로드캐스트를 볼 수 있다.
- **재연결은 pending connect 로 한다.** CoreBluetooth 의 `connect()` 는 타임아웃이
  없어서, 끊긴 즉시 걸어두면 주변장치가 다시 광고하는 순간 시스템이 붙여준다.
  폴링 루프보다 빠르고 배터리에도 유리하다.
- **마지막 값을 지우지 않는다.** 끊겨도 값은 남기고 회색으로만 바꾼다.
  화면이 비어버리면 "지금 안 보이는 게 끊긴 건지 값이 0인 건지" 구분이 안 된다.
- **모든 화면에 실측 진단값이 있다.** 기대치가 아니라 실측 Hz 를 보여줘서
  "잘 되는 것 같다"가 아니라 숫자로 판정한다.

## 지금 어디까지 왔나 (2026-08-22)

### 되는 것 — 실기기로 확인한 것만

| | |
|---|---|
| BLE | `SAIL-random()` 광고 · 10 Hz notify · 37바이트 확장 패킷 (MTU 255) |
| GPS (RAK12501) | **115200bps / 10 Hz**, GGA·RMC 만, GPS+BeiDou+GLONASS. 체크섬 실패 0 |
| IMU (RAK1905) | 9축 실측. 자이로 0점 자동, 힐 0점은 `level` |
| 화면 (RAK1921) | 속도·COG·HDG·힐·9축. 값이 없으면 `NO GPS FIX` + 위성 수 |
| 배터리 | GPIO1 실측 + 리튬폴리머 방전 곡선 |
| 아이폰 앱 | 라이브 / 상세 / 설정. 상세는 스크롤 없이 한 화면 |
| 워치 앱 | 좌우 3페이지. 속도 → 센서 상세 → 설정 |
| 멈춤 방지 | I2C 타임아웃 · 센서 격리와 자동복구 · 워치독 30초 |

**아직 실외에서 위성을 잡아본 적이 없다.** 문장은 10 Hz 로 깨끗하게 들어오지만
값은 전부 비어 있어서, 속도·침로 자리에 `--.--` 와 `NO GPS FIX` 가 떠 있는 상태다.

**시뮬레이터는 걷어냈다.** 예전에는 위성을 못 잡으면 지어낸 5~7 kn 을 채우고
`(SIM)` 을 붙였는데, 화면에 그럴듯한 숫자가 떠 있으면 사람은 그걸 읽는다.
지금은 값이 없으면 없다고 보낸다 — 자세한 규약은 `PROTOCOL.md` §2.1.

### 속도·침로 — 다음 세션이 이어받을 조사

지금은 `$GNRMC` 의 속도·침로 필드를 **그대로 쓴다.** 필터가 하나도 없다.
요트에서는 이게 문제가 된다.

**두 가지 계산 방식이 있다.**

| | 원리 | 강점 | 약점 |
|---|---|---|---|
| 도플러 | 반송파 주파수 편이 | 분산이 작다. 고속(30 kn+)에서 특히 | — |
| 위치 차분 | 두 위치의 차 ÷ 시간 | **평균값이 더 정확** | 분산이 크고 이상치가 튄다 |

> "the position-based speed data has a greater variance than the Doppler-based
> speed data, [but] has a more accurate mean value" — 두 방식은 상보적이고,
> 잘 합치면 각각보다 정확해진다.

L76K 가 주는 값이 어느 쪽인지는 아직 확인 못 했다. 도플러일 가능성이 크다.

**저속에서 COG 가 튄다.** 배가 느리면 위치 오차가 방향 계산을 지배한다.
정박 중이거나 미풍일 때 침로가 빙빙 도는 이유다. 이때는 자력계 방위(HDG)가
더 쓸모 있다 — 그래서 화면에 둘을 나란히 뒀다.

**참고 논문**
- *Five-State Extended Kalman Filter for Estimation of SOG, COG and Course Rate
  of Unmanned Surface Vehicles: Experimental Results* (PMC8659471)
  — 우리와 같은 문제를 다룬다. GNSS 위경도만으로 SOG·COG·침로변화율을 추정.
- *Accuracy of non-differential GPS for the determination of speed over ground*
  (ScienceDirect S0021929004001204)

**단계적으로 접근할 것.** EKF 를 바로 넣지 말고 —
1. 먼저 밖에서 날것 그대로의 값이 얼마나 튀는지 **기록해서 본다** (SD 로깅이
   여기에 쓰인다)
2. 저속에서 COG 를 억제하는 규칙부터 (예: SOG 가 임계 아래면 COG 를 붙들거나
   HDG 로 대체)
3. 그래도 부족하면 필터

숫자를 보기 전에 필터부터 넣으면 무엇을 고쳤는지 알 수 없다.

### 미뤄둔 판단

- **힐에 상보 필터** — 지금은 가속도계만. 파도에 출렁일 수 있는데, 바다에서
  실제로 출렁이는지 보고 나서 넣기로 했다.
- **HDG 보정** — 기울기 보정과 자기 편각(한국 약 8도 서편)이 빠져 있다.
- **GPS 가 먹통이 됐을 때 복구** — 지금은 부팅 때 한 번만 깨운다. 몇 분간
  문장이 안 오면 전원을 껐다 켜는 장치가 없다.
- **`firmware/` (Feather) 를 계속 둘지** — 안 쓰지만 검증에는 들어간다.

### 알아두면 좋은 것

- **워치 Always On 이 안 걸린 적이 있다.** 코드(`isLuminanceReduced` 로직)는
  멀쩡했고 워치를 만지니 돌아왔다. 원인은 끝내 못 가렸다.
  설정 페이지 진단의 **`어두워짐` 횟수**가 0 이면 같은 증상이다.
- **GPS 는 PMTK 가 아니라 PCAS 명령을 쓴다.** 검색에서 본 MediaTek 명령을
  그대로 썼다가 통신이 통째로 깨졌다. 모듈 문서를 먼저 볼 것.
- **WiFi 비밀은 `firmware-rak/include/secrets.h`** — `.gitignore` 로 막혀 있고
  아직 어디에도 안 쓴다.
- **워치 앱은 명령줄로 못 넣는다.** Xcode ⌘R 만 된다 (`app/README.md` 참고).
