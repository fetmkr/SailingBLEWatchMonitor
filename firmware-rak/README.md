# firmware-rak — Sailing Monitor 텔레메트리 모듈 (RAK3112 / WisBlock)

`firmware/` (Adafruit Feather TFT) 와 **완전히 분리된** 프로젝트다.
칩은 둘 다 ESP32-S3 지만 보드·핀·붙는 모듈이 전부 다르다.
되던 것을 건드리지 않으려고 폴더를 나눴다.

| | |
|---|---|
| 코어 모듈 | **RAK3312** (WisBlock Core). 안에 든 스탬프 모듈이 **RAK3112** |
| 칩 | ESP32-S3 + SX1262 (LoRa), 16 MB 플래시 / 8 MB PSRAM |
| 베이스 보드 | **RAK19007** WisBlock Base 2nd Gen (USB-C, 30x60 mm) |
| 프레임워크 | Arduino (PlatformIO) |
| BLE 스택 | NimBLE-Arduino 2.5.x |
| 시리얼 | 115200 baud (USB CDC) |

프로토콜은 [`../PROTOCOL.md`](../PROTOCOL.md) 를 따른다.

> **프로토콜을 고칠 때는 세 곳을 함께 고쳐야 한다.**
> `firmware/include/protocol.h` · `firmware-rak/include/protocol.h` · `app/Shared/Protocol.swift`
> 각자 자기 사본을 갖는 구조라 한쪽만 고치면 조용히 어긋난다.

## 2. 센서 전원 핀 — 실측으로 판정 끝

문서끼리 값이 달랐다.

| 출처 | WB_IO2 |
|---|---|
| RAK3312 datasheet | **GPIO14** |
| RAK 배포 `pins_arduino.h` | GPIO2 (14 는 주석 처리돼 있음) |

**실기기 판정 결과 GPIO14 가 맞다.** (2026-08-21, MAC `3C:DC:75:70:2F:B5`)

| 설정 | GPS 응답 |
|---|---|
| `power 14` | **1380 바이트** |
| `power 2` | 없음 |
| `power off` | 없음 |

datasheet 가 맞고 RAK 이 배포하는 `pins_arduino.h` 가 틀렸다. 그래서 이 코드는
그 파일의 `WB_IO2` 매크로를 쓰지 않고 `board_rak.h` 에서 직접 정의한다.

### 판정에 IMU 를 쓰면 안 된다

여기서 한 번 헛짚었다. 처음엔 `scan` 으로 판정하려 했는데 **전원을 꺼도
IMU 가 계속 보였다.**

| 모듈 | 전원을 어디서 받나 |
|---|---|
| **RAK1905 IMU** | 커넥터 핀9/16 **VDD** — 늘 켜져 있음. 스위치와 무관 |
| **RAK12501 GPS** | 커넥터 핀11/14 **3V3_S** — 스위치가 달린 쪽 |

그래서 전원 핀 판정은 `gps` 명령으로 한다. `scan` 은 판정 근거가 못 된다.

판정 결과는 NVS 에 저장되므로 재부팅해도, 다시 구워도 유지된다.

> Feather TFT 에서 `TFT_I2C_POWER` 를 안 올려 화면이 안 켜졌던 것과 같은 함정이다.
> 다만 이번엔 모듈마다 먹는 전원이 달라서, 한 모듈이 보인다고 스위치가
> 켜진 것은 아니다.

## 3. 붙어 있는 모듈과 자리 배치

| 모듈 | 칩 | 통신 | 자리 |
|---|---|---|---|
| **RAK12501** GPS | Quectel L76K | UART **115200 / 10 Hz** | 센서 슬롯 **A** |
| **RAK1905** IMU | TDK MPU-9250 (9축) | I2C `0x68` | 센서 슬롯 **C** |
| **RAK1921** 화면 | SSD1306 128x64 | I2C `0x3C` | **J12 헤더** |
| **RAK15002** SD | — | SPI | **IO 슬롯** |

화면과 SD 는 센서 슬롯을 쓰지 않는다. 화면은 2.54 mm I2C 헤더(J12)에 꽂고,
SD 는 IO 슬롯 전용이다. 그래서 센서 슬롯 A~D 를 놓고 다투는 것은 GPS 와 IMU
둘뿐이고, 두 자리가 남는다.

### GPS 는 슬롯 A 에

이유가 두 가지다.

**1) GPS 모듈은 커넥터 핀10 을 RESET 으로 받는다.** 그 핀이 슬롯마다 다르다.

| 슬롯 | 핀10 | |
|---|---|---|
| A | IO2 | 센서 전원 스위치와 같은 선 |
| D | IO6 = GPIO39 | 따로 HIGH 로 올려야 함 |

A 에 꽂으면 전원을 켜는 동작이 그대로 리셋 해제가 된다. RAK 예제가 바로 이걸
전제로 짜여 있다. D 에 꽂았다면 `gps d` 명령을 쓴다 (IO6 을 대신 흔들어 준다).

**2) 슬롯 D 는 SD 카드와 부딪힌다.** RAK15002 는 카드 삽입 감지를 커넥터
핀38 = IO6 = GPIO39 로 낸다. GPS 를 D 에 꽂으면 GPS 의 RESET 과 SD 의 카드감지가
**같은 GPIO39 에서 서로 싸운다.**

### IMU 는 슬롯 C 에

RAK1905 의 인터럽트는 슬롯마다 다른 핀으로 나온다.

| 슬롯 | A | B | C | D |
|---|---|---|---|---|
| 인터럽트 | IO1 | **IO2** | IO3 | IO5 |

B 의 IO2 는 센서 전원 스위치와 겹친다. C 의 IO3(GPIO41)이 전용이라 안전하다.

### 그 밖에 지킬 것

- **UART 는 A·D 에만.** B·C 는 그 핀이 회로도에서 끊겨 있다(NC).
- **SPI 모듈은 하나만.** 칩셀렉트가 네 슬롯 공통이라 두 개면 동시에 깨어난다.
  지금은 SD 하나뿐이라 문제없다.
- **I2C 는 I2C1 한 줄뿐.** 화면과 IMU 가 같은 버스에 매달린다. 주소가
  `0x3C` 와 `0x68` 로 달라서 부딪히지 않는다. 풀업은 베이스보드에 이미 있다
  (R10~R13, 각 4.7k).

## 4. 빌드 · 플래시

```bash
cd firmware-rak
pio run
pio run -t upload
```

보드 정의는 저장소 안에 들어 있다 (`rakwireless/`). 따로 설치할 게 없다.

> 출처: [RAKWireless/WisBlock](https://github.com/RAKWireless/WisBlock)
> `examples/RAK3112/IDE-Patches/PlatformIO/rakwireless/`, 커밋 `ae4137bb` (2026-07-23)

네이티브 USB 라 PlatformIO 가 1200bps 터치로 알아서 부트로더에 들어간다
(보드 정의에 `use_1200bps_touch`, `wait_for_upload_port` 가 이미 있다).
안 되면 RAK19007 의 `RESET` 버튼을 누른 채 `BOOT` 를 눌렀다 떼고 다시 올린다.

```bash
pio device list                     # 포트 확인
pio device monitor                  # 시리얼 (115200)
```

## 5. 시리얼 명령

| 명령 | 설명 |
|---|---|
| **`check`** | **붙어 있는 것을 한 번에 훑는다. 처음 구웠으면 이것부터** |
| `fix` | GPS 파싱 상태 — 위성 수, 위치, 속도, 침로, 체크섬 |
| `imu` | 9축 값 5초 출력. 보드를 기울여 보면 값이 따라온다 |
| `scan` | I2C — 화면 `0x3C` / IMU `0x68` 확인 |
| `sd` | SD카드 마운트 + 쓰기 시험 |
| `gps` | UART1 원시 NMEA 5초 (GPS 가 슬롯 A) |
| `gps d` | 같은 것 (GPS 가 슬롯 D 일 때) |
| `batt` | 배터리 전압 실측 |
| `calib` | 자이로 0점 다시 잡기 (기울어 있어도 OK, 멈춰만 있으면 됨) |
| `level` | 지금 자세를 힐 0° 로 삼기 (§8) |
| `oled` | 화면을 나중에 꽂았을 때 다시 붙이기 |
| `power 14` / `power 2` / `power off` | 센서 전원 핀 (§2) |
| `name <이름>` | 보드 이름. 최대 11자, 영숫자/`-`/`_` |
| `hz <1~100>` | notify 주기 |
| `info` | 현재 설정 |
| `help` | 도움말 |

이름을 설정하지 않으면 MAC 뒤 2바이트로 자동 생성된다 (`SAIL-75D5` 형태).

`scan` 은 붙어 있어야 할 것과 대조해서 알려준다.

```
  I2C1 — 센서 슬롯 A~D + J12 헤더 (SDA GPIO9 / SCL GPIO40)
    0x3C  ★ SSD1306 화면 — RAK1921 (J12 헤더)
    0x68  ★ MPU-9250 IMU — RAK1905
  ──────────────────────────────────────────
  화면 RAK1921 (0x3C)  보임
  IMU  RAK1905 (0x68)  보임
```

`imu` 는 `WHO_AM_I` 로 칩을 확인하고 기울기를 5초 동안 뿌린다.
보드를 좌우로 기울여 값이 따라 움직이면 힐 실측을 붙일 수 있다는 뜻이다.
라이브러리 없이 레지스터를 직접 읽으므로 의존성이 늘지 않는다.

## 6. 배터리 전압

RAK19007 회로도에서 읽은 분압이다.

```
VBAT ──[R3 1M]──┬──[R4 1.5M]── GND
                │
             ADC_VBAT ──[R7 0Ω]── 코어 핀21(AIN0) = GPIO1
```

핀에 걸리는 전압은 배터리의 `1.5 / (1.0 + 1.5) = 0.6` 배다. 되짚으면 나누기 0.6.

| 배터리 | GPIO1 |
|---|---|
| 4.2 V (만충) | 2.52 V |
| 3.3 V (바닥) | 1.98 V |

교차검증: 두 저항을 더하면 2.5 MΩ 이라 4.2 V 에서 1.68 µA 가 샌다.
datasheet 의 "모듈 없을 때 누설 2 µA" 와 맞는다.

실측 (2026-08-21)

| 상태 | GPIO1 | 환산 |
|---|---|---|
| USB 만, 배터리 없음 | 2487 mV | 4.145 V |
| **배터리 꽂음 (충전 중)** | **2358 mV** | **3.930 V** |

두 번 재서 2 mV 차이로 안정적이다. 2.5 MΩ 분압이라 값이 처질까 걱정했는데
그렇지 않았다.

> **멀티미터 대조는 아직 안 했다.** 어긋나면 `board_rak.h` 의
> `kBattCorrection` 을 조정할 것.
>
> USB 가 꽂혀 있으면 충전 중이라 실제보다 높게 나온다. 진짜 잔량은 USB 를
> 뽑고 재야 한다.

### 잔량은 직선이 아니라 곡선으로 환산한다

리튬폴리머는 전압과 잔량이 직선 관계가 아니다. 처음에 3.3~4.2 V 를 직선으로
잡았더니 낮은 전압에서 잔량을 크게 부풀렸다.

| 전압 | 직선 계산 | 곡선 (지금) |
|---|---|---|
| 3.93 V | 70 % | 72 % |
| 3.82 V | 58 % | 50 % |
| **3.70 V** | **44 %** | **13 %** |
| 3.68 V | 42 % | 10 % |

**곧 꺼질 배터리가 44 % 로 보이면 바다에서 위험하다.** 그래서 꺾은선 표
(`kBattCurve`)를 두고 사이를 직선 보간한다.

## 7. 지금 어디까지 왔나

**1단계 (지금).** 텔레메트리는 아직 **가상 데이터**다. `firmware/` 와 똑같은
시뮬레이터를 쓴다. 값이 기존 보드와 같아야, 뭔가 이상할 때 앱 문제인지
보드 문제인지 가릴 수 있다.

| 단계 | 내용 | 상태 |
|---|---|---|
| 1 | 새 보드에서 BLE 광고·연결·notify | **끝** |
| 2 | 전원 핀 판정 + 모듈이 살아 있는지 확인 | **끝** |
| 3 | GPS 로 속도·침로, IMU 로 힐 실측 | **끝** (야외 확인 남음) |
| 4 | 화면에 값 표시 | **코드 끝** (화면 꽂으면 확인) |
| 5 | SD 에 기록 | 카드 넣은 뒤 |

## 8. 값을 어디서 가져오나

| 값 | 어디서 | 못 쓸 때 |
|---|---|---|
| **SOG·COG** | GPS (위성을 잡았을 때만) | 시뮬레이터로 채움 |
| **HDG** | 자력계 | `---` 로 표시 |
| **HEEL·PITCH** | 가속도계 (**언제나**) | IMU 가 없을 때만 시뮬레이터 |
| **GYR** | 자이로 | — |
| **BATT** | GPIO1 ADC | — |

힐은 GPS 와 무관하다. **GPS 는 배가 얼마나 기울었는지 알려주지 못한다.**
그래서 위성을 못 잡은 실내에서도 힐만은 진짜 값이 나온다.

### COG 와 HDG 는 다른 값이다

| | 무엇 | 언제 안 나오나 |
|---|---|---|
| **COG** | 배가 **실제로 가는 방향** (GPS) | 배가 멈춰 있으면 |
| **HDG** | **뱃머리가 보는 방향** (자력계) | 자력계가 죽으면 |

요트에서는 조류와 바람 때문에 이 둘이 벌어진다. 그래서 나란히 보여준다.

> **HDG 는 아직 거친 값이다.** `atan2(mag.y, mag.x)` 만 쓴다.
> 기울기 보정과 자기 편각(한국은 약 8도 서편)이 빠져 있다.
> 배에 달고 실제 방위와 대조한 뒤에 넣는다.

> **힐·피치도 한계가 있다.** 가속도계는 중력과 배의 가속을 구별하지 못한다.
> 파도에 배가 흔들리면 힐 값이 같이 출렁일 수 있다. 자이로와 섞으면
> (상보 필터) 안정되지만, 바다에서 실제로 출렁이는지 보고 나서 넣기로 했다.

### GPS 갱신율과 위성

L76K 는 켜지면 **1 Hz / 9600bps** 로 시작한다. 1초에 한 번이면 배가 방향을 트는
동안 값이 몇 번 안 바뀌어서 화면이 굼떠 보인다. notify 를 10 Hz 로 쏴도 같은
숫자가 열 번 반복될 뿐이다. 그래서 부팅할 때마다 다시 건다.

> **★ 이 모듈은 PMTK(MediaTek) 명령을 안 받는다. PCAS 명령을 쓴다.**
> 검색에서 본 `$PMTK251` 을 그대로 썼다가 모듈이 통신 속도를 안 바꿨고,
> 우리만 38400 으로 듣게 되어 들어오는 바이트가 전부 깨졌다
> (체크섬 통과 0). 모듈 문서를 먼저 봤어야 했다.

| 명령 | 하는 일 |
|---|---|
| `$PCAS04,7` | GPS + BeiDou + **GLONASS**. 기본값 3 은 GLONASS 가 꺼져 있다 |
| `$PCAS03,1,0,0,0,1,0,0,0,...` | **GGA 와 RMC 만** 남기고 다섯 종류를 끈다 |
| `$PCAS01,5` | 115200 bps |
| `$PCAS02,100` | 10 Hz |

순서가 중요하다. 문장을 줄이고 통신 속도를 올린 **다음에** 갱신율을 올린다.
문서도 못을 박는다 — *"It is required to set the type of NMEA sentences output to
single and change the baud rate to 115200 bps when the `<Interval>` is less than 1000."*
9600bps 는 초당 960바이트뿐인데 NMEA 한 벌이 400~500바이트다.

**10 Hz 는 문서에 없는 값이다.** `$PCAS02` 설명에는 1000/500/200(1·2·5 Hz)까지만
적혀 있고 Meshtastic 같은 실제 구현도 갱신율을 안 건드린다. 제품 사양에만
"up to 10 Hz" 라고 있어서 넣어 보고 실측으로 확인했다.

```
요청 10 Hz → 5초 동안 문장 98개 (초당 19.6개)
             GGA+RMC 두 종류이므로 초당 9.8 회 갱신, 체크섬 실패 0
```

`gpshz <1|2|5|10>` 로 바꿀 수 있고, **바꾼 뒤 5초 동안 문장을 세서 실제로
걸렸는지 알려준다.** 말로만 바뀌는 경우가 있어서 넣었다.

> 설정은 모듈 전원이 끊기면 날아간다. 그래서 부팅할 때마다 다시 건다.
> 보드만 리셋되고 모듈은 안 꺼진 경우도 있어서, 9600 과 115200 양쪽으로
> 명령을 보낸다. 못 알아듣는 쪽은 그냥 버려진다.

### 자이로 0점

MPU-9250 은 가만히 있어도 자이로가 0 이 아니다. 이 보드는 책상에 그냥 뒀는데
`-0.5 / +0.9 / +1.1 °/s` 가 계속 나왔다. 흔들린 게 아니라 값이 그 자리에
머물러 있었다 — **드리프트가 아니라 영점이 어긋난 것이다.**

부팅할 때마다 정지 상태에서 64번 재서 평균을 빼준다. NVS 에 저장된다.

```
[IMU] 자이로 0점 잡음 — 원시 -59 111 126 (= -0.45 0.85 0.96 °/s) 만큼 빼둡니다

전:  자이로  -0.5  +0.9  +1.1 °/s
후:  자이로  +0.0  +0.1  +0.0 °/s
```

재는 동안 흔들렸으면(원시값 폭 500, 약 3.8 °/s 초과) 포기하고 지난 값을 쓴다.

**자이로 0점은 자세와 무관하다.** 기울어 있어도, 뒤집혀 있어도 멈춰 있기만
하면 제대로 잡힌다. 그래서 `calib` 을 배 위에서 써도 안전하다.

> 라이브러리의 `autoOffsets()` 는 쓰지 않는다. 그건 가속도 0점까지 함께
> 건드려서, 배가 기울어 있을 때 부르면 힐이 통째로 어긋난다.
> 설치 각도는 `level`, 자이로 영점은 `calib` 으로 따로 다룬다.

### 시뮬레이터로 채운 값은 반드시 표시한다

로그에서 값 옆의 괄호가 그 값의 출처다.

```
[  42.0s] SAIL-2FB5 | SOG  5.61 kn (SIM) | COG  45.0° (SIM) | HEEL  -18.1° (IMU) | BATT  94% | seq 42 | ADVERTISING
   GPS  위성 0 | 아직 못 잡음
   9축  가속 -0.09 -0.08 -0.99 g | 자이로 +0.1 -0.2 +0.0 °/s | 자력 +12.3 -34.5 +56.7 µT | roll -175.5° pitch +5.0°
```

`(SIM)` 은 위성을 못 잡아 지어낸 값이라는 뜻이다. 가짜 값이 실측처럼 보이면
바다에서 엉뚱한 판단을 하게 된다.

### 낡은 값을 걸러낸다

GPS 를 한 번 잡았다가 놓쳐도 파서는 마지막 값을 그대로 들고 있다. 그래서
`age()` 로 3초가 지난 값은 버리고 시뮬레이터로 되돌린다. 이게 없으면 신호가
끊긴 뒤에도 옛날 속도를 계속 진짜인 양 내보내게 된다.

### 힐 0점 — `level` 명령

센서가 내놓는 각도는 **보드를 어느 방향으로 달았느냐에 따라 통째로 치우친다.**

실제로 책상에 뒤집어 놓고 재니 `roll` 이 `-177.9°` 로 나왔다. 그대로 쓰면
배가 늘 뒤집힌 것으로 보이고, 프로토콜의 힐은 -128~127 범위라 잘려 나간다.

그래서 "지금 이 자세가 평형" 이라고 알려주는 기준각을 따로 둔다.

```
level
```

지금 각도를 힐 0° 로 삼는다. NVS 에 저장되므로 재부팅해도, 다시 구워도 남는다.

> **배를 물에 띄우고 평형일 때 다시 잡아야 한다.** 책상에서 잡은 기준은
> 배 위에서 맞지 않는다.

### `level` 과 `calib` 은 다른 것이다

| 명령 | 무엇을 고치나 |
|---|---|
| `level` | **보드를 어떻게 달았는지** — 설치 각도의 치우침 |
| `calib` | **센서 자체의 오차** — 가속도계·자이로의 0점 |

보통은 `level` 만 있으면 된다.

### IMU 0점을 부팅 때 잡지 않는 이유

라이브러리의 `autoOffsets()` 는 "지금 평평하고 멈춰 있다" 를 전제로 0점을
잡는다. 배 위에서 부팅하면 그때 기울어져 있던 각도가 0 이 되어 힐이 통째로
어긋난다. 그래서 부팅 때는 부르지 않고, 배가 평평할 때 `calib` 명령으로만
잡는다.

### 아직 안 정한 것

- **어느 축이 힐인가.** 지금은 `roll` 을 쓴다. 보드를 배에 실제로 달아 보고
  `pitch` 가 맞으면 `buildTelemetry()` 의 한 줄만 바꾸면 된다.
- **자력계를 어디에 쓸까.** 배가 멈춰 있으면 GPS 침로(COG)가 나오지 않는다.
  자력계는 멈춰 있어도 뱃머리 방위를 준다. 둘은 다른 값이라 프로토콜에
  따로 실을지 정해야 한다.
- **"값 없음" 을 어떻게 보낼까.** 지금 12바이트 패킷에는 그런 표시가 없다.
  그래서 시뮬레이터로 채우고 있는 것이다.

### 1·2단계 실기기 결과 (2026-08-21)

보드 MAC `3C:DC:75:70:2F:B5` → 이름 `SAIL-2FB5`, `module_id` 183 (0xB7)

| 항목 | 결과 |
|---|---|
| BLE 광고 | `SAIL-2FB5` / ADV_IND / 10 Hz notify — 정상 |
| 센서 전원 | **GPIO14** 확정 (§2) |
| IMU RAK1905 | `WHO_AM_I` = `0x71` = MPU-9250. 세 축 합이 1 g — 정상 |
| GPS RAK12501 | NMEA 정상, `$GPTXT,...,ANTENNA OK`. 실내라 아직 위성 못 잡음 |
| 화면 RAK1921 | 아직 안 달았음 |
| SD RAK15002 | 카드 감지 HIGH = 카드 없음. 마운트 실패 |
| 배터리 | GPIO1 에서 2487 mV → 4.145 V. 멀티미터 대조는 아직 |

ADC 소스 임피던스가 2.5 MΩ 이라 값이 처질까 걱정했는데, 실제로는 분압비와
맞아떨어지는 값이 나왔다 (`4.145 × 0.6 = 2.487`). 그래도 멀티미터로 한 번은
대조할 것.

3·4단계에서 새로 붙일 라이브러리는 화면용 `U8g2` 와 GPS 파싱용 `TinyGPSPlus`
둘뿐이다. IMU 와 SD 는 지금도 라이브러리 없이 읽고 있다.

**IMU 가 자력계까지 갖고 있다.** MPU-9250 안에 AK8963 이 들어 있어서 배가
멈춰 있어도 뱃머리 방위를 잴 수 있다. GPS 의 침로(COG)는 배가 움직여야
나오므로, 정박 중이거나 아주 느릴 때는 이 둘이 서로 다른 값이 된다.
프로토콜에 방위를 따로 실을지 4단계에서 정한다.

**앞으로 정해야 할 것.** 지금 12바이트 패킷에는 "값 없음" 이 없다.
GPS 가 위성을 못 잡았을 때 속도 0 을 보내면 앱에서 배가 멈춘 것과 구별되지 않는다.
4단계 전에 프로토콜을 손봐야 한다.

## 9. 화면 (RAK1921, 128x64)

화면을 안 꽂아도 펌웨어는 그대로 돈다. 부팅할 때 `0x3C` 응답을 확인해서
없으면 조용히 지나간다. **나중에 꽂았으면 `oled` 명령을 치면 바로 붙는다.**
재부팅할 필요 없다. `scan` 을 쳐도 자동으로 붙인다.

```
    0                                      127
 0  ┌──────────────────────────────────────┐
 7  │ random()               BLE*     94%  │  이름 / BLE / 배터리
 9  ├──────────────────────────────────────┤
27  │                             ██SIM██  │  ← 흑백을 뒤집어 그린다
30  │  6.38 kn                             │  ← 18px, 제일 큼
41  │ COG 045       HDG 344                │
49  │ HEEL  -1.9   PITCH  +2.9             │
56  │ GYR  -0.5  +0.9  +1.1                │
63  │ ACC +0.04 -0.08 -1.00                │
    └──────────────────────────────────────┘
```

배에서 제일 먼저 눈에 들어와야 하는 건 속도다. SOG 만 18픽셀로 쓰고 나머지는
작게 깔았다. SOG 는 왼쪽, `SIM` 은 오른쪽이라 세로로 겹쳐도 서로 침범하지 않는다.

| 표시 | 뜻 |
|---|---|
| `ADV` / `BLE` / `BLE*` | 광고 중 / 연결됨 / 앱이 값을 받는 중 |
| `SIM` | 속도가 시뮬레이터 값이다 (위성 못 잡음) |
| `H1.2` | 위성을 잡았고 HDOP 이 1.2 — 작을수록 정확 |
| `FIX` | 잡았지만 HDOP 을 아직 모름 |

**`SIM` 만 흰 박스에 검은 글씨로 뒤집어 그린다.** 지어낸 숫자를 실측으로
오해하면 바다에서 위험하다. 멀리서도 바로 눈에 띄어야 한다.

`COG` 와 `HDG` 를 나란히 둔 이유는 §8 참고. 자력계 원본 세 축은 `HDG` 로
대신하고 화면에서는 뺐다 (시리얼 로그에는 그대로 나온다).

글자가 128픽셀을 넘으면 화면에서는 그냥 잘려서 알아채기 어렵다. 그래서
그릴 때 실제 폭을 재서 넘치면 시리얼로 알린다 (`[OLED] ... 넘침`).

### ★ U8g2 에 I2C 핀을 넘기면 보드가 통째로 멈춘다

화면을 처음 꽂았더니 펌웨어가 아예 멈췄다. 1 초 로그조차 안 나왔다.
단계별로 로그를 찍어 보니 `initDisplay()` 에서 멈춰 있었다.

원인은 U8g2 가 **넘겨받은 핀을 `pinMode(핀, OUTPUT)` 으로 바꿔 버리는 것**이다.

```
U8x8lib.cpp  U8X8_MSG_GPIO_AND_DELAY_INIT
             → i < U8X8_PIN_OUTPUT_CNT 이면 pinMode(pin, OUTPUT)
clib/u8x8.h  U8X8_PIN_I2C_CLOCK = 12,  U8X8_PIN_I2C_DATA = 13
             U8X8_PIN_OUTPUT_CNT = 16      ← 둘 다 이 안에 든다
```

I2C 는 오픈드레인이어야 하는데 푸시풀 출력이 되면 버스가 죽는다. 화면만
안 켜지는 게 아니라 **같은 버스에 매달린 IMU 까지 함께 멈춰서** 펌웨어 전체가
정지한다.

그래서 생성자에 핀을 넘기지 않는다.

```cpp
U8G2_SSD1306_128X64_NONAME_F_HW_I2C gOled(U8G2_R0);   // 핀 안 넘김
```

핀을 안 넘겨도 우리가 쓰는 GPIO9/40 으로 간다. `main` 이 먼저
`Wire.begin(SDA, SCL, 400000)` 을 해 두면, U8g2 가 부르는 `Wire.begin()` 은
이미 초기화된 버스를 보고 그냥 통과하기 때문이다.

```
Wire.cpp   if (i2cIsInit(num)) { started = true; goto end; }
```

> **그래서 `displayBegin()` 은 반드시 `Wire.begin()` 뒤에 불러야 한다.**
> 지금은 `imuBegin()` 이 Wire 를 먼저 열고 그다음 화면을 붙인다.

## 10. 멈추지 않기 위한 장치

센서 하나가 죽었다고 계기가 통째로 멈추면 안 된다. 바다에서는 그게 제일
위험하다. 실제로 화면 초기화 한 줄 때문에 I2C 버스가 죽어 펌웨어 전체가
정지한 적이 있다 (§9). 그때는 아무 로그도 안 나와서 원인을 찾는 데 오래 걸렸다.

세 겹으로 막는다.

| 겹 | 무엇을 막나 |
|---|---|
| **I2C 타임아웃 50 ms** | 버스가 물려도 오래 붙들려 있지 않는다 |
| **격리와 재연결** | 응답이 끊긴 센서는 끄고 나머지로 계속 간다. 다시 나타나면 붙는다 |
| **워치독 30초** | 그래도 어딘가에서 멈추면 보드를 다시 시작시킨다 |

### 격리와 재연결

1 Hz 로 각 I2C 장치를 두드려 본다.

- **IMU 가 사라지면** 힐을 시뮬레이터 값으로 돌린다. BLE 는 계속 돈다.
- **화면이 사라지면** 그리기만 멈춘다. 나머지는 그대로다.
- **다시 꽂히면** 알아서 붙는다. 재부팅할 필요 없다.

```
[IMU]  응답이 끊겼습니다 — 힐을 시뮬레이터 값으로 돌립니다
[OLED] 응답이 끊겼습니다 — 그리기를 멈춥니다 (나머지는 계속 돕니다)
[OLED] 다시 보입니다 — 붙입니다
```

### 워치독

`check` 명령 하나가 20초 넘게 걸리므로 30초로 잡았다. 몇 초씩 도는 진단
루프 안에서는 `feedWatchdog()` 으로 살아 있다고 알린다 — 그게 없으면 정상
동작 중에 리셋된다.

```
[WDT] 워치독 30초 — 멈추면 스스로 다시 시작합니다
```

## 11. 이 배의 이름

**`random()`** — 괄호까지가 이름이다.

BLE 광고에 `SAIL-random()` 으로 나가고 화면 좌측 상단에도 그대로 뜬다.
`module_id` 는 160 (0xA0).

이름 필터가 영숫자와 `-`, `_` 만 남기고 있어서 괄호가 잘렸다. `sanitizeName()`
에서 `(` `)` 를 허용하도록 고쳤다.

> SD 카드 로깅처럼 **파일 이름을 만드는 기능**을 붙일 때는 괄호가 들어가도
> 되는지 따로 확인할 것.
